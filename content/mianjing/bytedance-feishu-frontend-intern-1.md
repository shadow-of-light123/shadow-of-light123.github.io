## 面试问题

### 1. Vue2 和 React 18 的差异

**回答**：核心差异在**数据更新模型**和**编程范式**两个层面。

| 维度     | Vue                                                                | React                                                                          |
| -------- | ------------------------------------------------------------------ | ------------------------------------------------------------------------------ |
| 数据更新 | 响应式：Proxy 拦截读写，自动依赖收集，数据变化精确触发对应组件更新 | 不可变数据：setState 显式触发调度，从组件开始重新执行渲染函数，配合 fiber diff |
| 模板     | SFC 单文件组件，template 模板语法                                  | JSX，在 JS 里写视图，一切皆 JavaScript                                         |
| 逻辑组织 | 组合式 API（setup）                                                | hooks 函数式编程，useState / useEffect 管理状态和副作用                        |
| 生态     | 官方全家桶（Vue Router、Pinia）                                    | 官方只管视图层，路由/状态管理靠社区生态                                        |
| 优化心智 | 响应式自动精确更新，优化负担小                                     | 需要手动 memo / useMemo / useCallback 避免多余重渲染                           |

一句话：Vue 是「数据变了框架自动找到该更新的地方」，React 是「数据变了重新渲染，框架帮你 diff 出该更新的地方」。

### 2. Vue 和 React 在组件复用上的不同

**回答**：分「UI 复用」和「逻辑复用」两类。

- **UI 复用**两边思路一致：拆组件 + props 配置化 + 插槽/slot（React 是 children 或 render props）
- **逻辑复用**：Vue2 用 mixins（有命名冲突、来源不清晰的问题），Vue3 转向组合式函数（composables）；React 从 HOC、render props 演进到自定义 hooks，是目前的主流
- **项目实践**：实习时基于组件库二次封装了大表格组件——columns 列配置、操作列按钮、删除确认弹窗、分页器全部收敛进组件内部，外部通过 props 传配置即可使用。公共逻辑（删除弹窗、分页参数管理）封装在组件里，业务方只关心列定义和数据源

### 3. Vue 和 React 在数据管理 / 数据流上的不同

**回答**：

- **相同点**：都提倡单向数据流。父传子都是 props；子传父 Vue 用 `emit` 事件，React 用回调函数
- **全局状态**：Vue 用 Pinia，基于响应式系统，直接修改 state 即可，API 简单；React 用 Redux Toolkit，reducer 必须是纯函数、不可变更新（内部 Immer），异步靠 thunk，样板相对多
- **关键区别**：React 的状态必须交给 React 管理（setState / dispatch），框架才能感知变化并触发渲染；Vue 的响应式数据是「活的」，改了自动触发更新
- React 轻量场景可用 Context + useReducer，但 Context 值变化会导致所有消费组件重渲染，不适合高频更新

### 4. 基于菜单驱动的动态路由架构实现

**回答**：本质是「后端权限表驱动前端路由注册」。

1. **登录后**用 token 请求权限表，后端返回树形结构，每个节点包含路由路径、路由名称、`permission` 标识（true/false）
2. **路由分两类**：静态路由（登录页、404 等无需权限的页面）全量注册；动态路由（需要权限的页面）等权限表回来后处理
3. **递归解析权限表**：`permission` 为 true 的节点才通过 `router.addRoute()` 注册，false 的跳过——以此实现**页面级权限控制**
4. 菜单组件也基于同一份过滤后的权限表渲染，保证「能看到的菜单」和「能访问的路由」一致

### 5. 按钮级权限控制如何实现？切账号会发生什么？

**回答**：

**按钮级权限**：

- 封装 Vue 自定义指令 `v-permission`，传入按钮的权限码
- 权限码集合维护在一个 `Set` 里（查询 O(1)）
- 指令 `mounted` 钩子中判断权限码是否在 Set 中，不在则用 `el.parentNode.removeChild(el)` 把按钮从 DOM 移除

**切账号**（追问）：

- 切账号 = 重新登录，拿到新 token 后权限表会变化
- 需要做的事：清空 Pinia 里的用户信息和旧权限 Set → **重置路由 matcher**（把之前 addRoute 的动态路由全部 removeRoute，否则旧账号的路由还残留）→ 重新拉取权限表 → 重新解析注册 → 跳转首页
- 容易漏的点：已缓存的页面标签页、keep-alive 缓存、接口缓存都要一起清掉

### 6. 已登录状态下新开 tab，输入管理页 URL 到页面展示的完整链路

**回答**：面试官强调的重点不是背八股，而是结合自己项目的**完整工程链路**。

**网络链路**：

1. URL 合法性校验与解析（不合法的输入会走搜索引擎而不是发请求）
2. DNS 解析：先查浏览器/系统/路由器缓存，未命中再递归查询
3. 静态资源命中**强缓存**直接复用，否则走**协商缓存**（带 ETag / If-None-Match 问服务端，304 则复用）
4. TCP 三次握手建连，HTTPS 再加 TLS 握手
5. 请求到服务端后：网关层做鉴权（校验 token）、限流、路由转发，再到静态资源服务 / 业务服务

**前端启动链路**（SPA 场景）：

1. 拿到 HTML 后解析：构建 DOM 树和 CSSOM 树（CSS 阻塞渲染、同步 JS 阻塞解析），合成渲染树，布局 + 绘制上屏
2. JS 执行，框架启动，进入**路由匹配**
3. 此时内存里 Pinia 是空的（新 tab / 刷新场景），路由守卫判断「有 token 但无用户信息」→ 先拉权限表 → 动态注册路由 → `next({ ...to, replace: true })` 重新导航匹配目标路由
4. 组件挂载后发接口请求数据，渲染页面

### 7. 强缓存和协商缓存分别用在什么场景

**回答**（面试时被追问应用场景没答上来，标准答案）：

- **强缓存**（`Cache-Control: max-age` / `Expires`）：适合**带内容 hash 的静态资源**——构建产物的 JS/CSS、图片、字体。文件名带 hash（`app.a1b2c3.js`），内容不变 URL 不变，可以放心设 `max-age=31536000, immutable` 缓存一年；内容变了 hash 必变，等于自动换 URL，缓存自然失效
- **协商缓存**（`ETag` / `Last-Modified`）：适合**不带 hash 但可能变化的资源**——典型是 `index.html` 入口文件。用 `no-cache` 让浏览器每次都问服务端「变了没」，没变返回 304 复用，变了返回新内容。这样发版后用户能立即拿到新入口，进而引用到新 hash 的静态资源
- **为什么这样组合**：强缓存省请求但拿新内容慢，协商缓存保证新鲜但还是要发一次请求。带 hash 的资源用前者换性能，入口 HTML 用后者保时效，两者配合实现「秒级发版 + 极致缓存」
- ETag 优于 Last-Modified 的原因：文件内容没变但 mtime 变了（如打开又保存）时，Last-Modified 会误判，而 ETag 基于内容 hash 只在真正变化时才变
- 补充：`no-store`（如敏感数据）完全不缓存；`no-cache` 是「缓存但每次使用前协商」，注意区分

### 8. HTTP 1.0 / 1.1 / 2.0 的区别

**回答**：

| 版本 | 核心特性                                                                             | 解决的问题                   |
| ---- | ------------------------------------------------------------------------------------ | ---------------------------- |
| 1.0  | 短连接，每个请求一个 TCP 连接                                                        | 最原始的形态，建连开销大     |
| 1.1  | **长连接**（keep-alive 默认开启）、Host 头支持虚拟主机、Range 断点续传、更多缓存控制 | 复用 TCP 连接，省去重复握手  |
| 2.0  | **二进制分帧**、**多路复用**、HPACK 头部压缩、服务器推送、流优先级                   | 解决 HTTP/1.1 应用层队头阻塞 |

- HTTP/1.1 的队头阻塞：同一连接上请求必须排队串行，前一个没返回后一个只能等
- HTTP/2 多路复用：同一 TCP 连接上跑多个流（stream），帧带流 ID 可乱序交错传输，一个流卡住不影响其他流
- 注意：HTTP/2 解决的是应用层队头阻塞，**TCP 层的队头阻塞依然存在**（丢包时整个连接等重传），这是 HTTP/3 改用 QUIC/UDP 的动机

### 9. 服务端推送有哪些方式？SSE 和 WebSocket 的区别

**回答**：三种方式——HTTP/2 Server Push、SSE、WebSocket，项目里实际用了后两种。

| 维度     | SSE                                       | WebSocket               |
| -------- | ----------------------------------------- | ----------------------- |
| 协议     | 基于普通 HTTP（`text/event-stream`）      | 独立协议，HTTP 101 升级 |
| 通信方向 | 单向（服务端 → 客户端）                   | 全双工                  |
| 数据格式 | 仅 UTF-8 文本                             | 文本 + 二进制           |
| 重连     | 浏览器自动重连，支持 `Last-Event-ID` 续传 | 需自己实现心跳 + 重连   |
| 底层     | TCP                                       | TCP                     |

**项目选型**：AI 对话的文本流式输出是单向场景，选 SSE；语音转写要持续上传音频二进制流、同时接收转写文本，是双向场景，选 WebSocket。

### 10. 打字机限速器怎么实现？不完整分片怎么处理？

**回答**：

**限速器**：为了平滑网络抖动、模拟打字机效果，不是收到一个 chunk 就立刻渲染。

1. 维护一个**缓冲区队列**，SSE 收到的文本解析后推入队列
2. `setInterval` 每 50ms 从队列取 15 个字符拼接到页面
3. 队列空了就暂停取，有新内容进来再继续——生产速度（网络）和消费速度（渲染）解耦

**不完整分片**（发生在流读取层，早于打字机队列）：

1. `ReadableStream` 的 `while` 循环里用 `TextDecoder` 解码，SSE 事件以 `\n\n`（或行内 `\n`）为边界
2. 按分隔符切分后，**最后一段如果没有分隔符结尾说明没传完**，不解析，留在 buffer 里
3. 下次循环读到新 chunk 时，拼在残留 buffer 后面再统一切分解析，保证每条消息完整

当时面试没讲清的点：打字机队列里都是已解析的纯字符，从单词中间截断无所谓（50ms 后下一轮就补上）；「不完整分片留到下次」发生在更早的流解码阶段，两个环节不要混在一起讲。

### 11. AI 思考过程和正文如何展示？用了几条 SSE 流？

**回答**：

- **一条流**。模型返回的 chunk 里用字段区分：`reasoning_content` 是思考片段，`content` 是正文
- 前端按字段分发渲染：思考内容用浅色背景 + 不同字体的折叠区块展示，正文正常渲染。不需要两条流——字段就是天然的信道标识
- 即使思考和正文交错出现也没关系，每次渲染只看当前 chunk 的字段归属

**追问补充**：「前端↔后端一条 SSE 流」和「后端↔模型服务一条流」是两段。后端要做**对话落库**——流式转发给前端的同时累积完整回答存库，用户关掉页面下次打开还能恢复历史对话。

### 12. 如何中止 AI 对话生成

**回答**：`AbortController`。

```js
const controller = new AbortController()

fetch('/api/chat', {
  method: 'POST',
  body: JSON.stringify({ messages }),
  signal: controller.signal, // 绑定信号
})

// 用户点击「停止」
controller.abort()
```

- `abort()` 后 fetch 的 Promise 会以 `AbortError` reject，流的 `reader` 读取同时终止
- 后端感知连接断开后应停止向上游模型生成并关闭流，避免 token 白烧
- 注意 catch 里要区分 `AbortError`（用户主动取消，不算错误）和真实网络错误

### 13. 实时语音转写的完整链路（Float32 → PCM16）

**回答**：链路是「浏览器采集 → 格式转换 → 分帧 → WebSocket 上行 → 后端调讯飞 SDK → 转写文本回推」。

1. **为什么不用浏览器自带方案**：Web Speech API 准确率不高、效果不好，改用讯飞实时 ASR 服务
2. **采集**：`AudioContext` + `getUserMedia` 拿麦克风音频流，出来的是 **Float32**（[-1, 1] 浮点采样）
3. **格式转换**：讯飞要求 **PCM16**，转换公式：`s < 0 ? s * 0x8000 : s * 0x7FFF`（即乘 32768），转换前要先 clamp 到 [-1, 1]
4. **分帧**：每帧 640 个采样点 × 2 字节 = **1280 字节**一包发送。16kHz 采样率下 640 采样点 ≈ 40ms 音频，是实时性和包体大小的平衡点——包太小头部开销占比高，包太大延迟高
5. **传输**：WebSocket 二进制帧发给后端，后端用讯飞 SDK 转发，转写结果通过同一条 WebSocket 推回前端展示

### 14. WebSocket 还在建连时用户已经开始说话，怎么处理

**回答**：建连有耗时，这段时间的音频帧不能丢也不能堵。

- 维护一个**建连前缓冲队列**：`readyState !== OPEN` 时音频帧先入队，`onopen` 后按顺序 flush 出去
- **队列设上限**：如果网络差迟迟建不了连，队列写满后**丢弃最旧的帧**（环形缓冲思路）——语音场景丢开头几帧比内存膨胀或音画严重延迟更可控
- 正常网络下建连很快，丢帧策略是兜底而非常态

### 15. 服务端收到两条重复消息怎么去重

**回答**：这是本场被追问暴露的薄弱点。当时的回答是「转写回来后按时间戳 + 内容去重」，面试官指出问题：**SDK 调用有成本，收到就盲目调下游付费 SDK，等于花两份钱只用一份结果**。

正确思路——**去重要发生在调用下游 SDK 之前，即幂等设计前置**：

1. 客户端为每条消息生成唯一 ID（消息序号 / uuid），重试时复用同一 ID
2. 服务端收到消息先查重：Redis `SETNX` 或布隆过滤器判断该 ID 是否已处理
3. 已处理过：直接返回缓存的结果，不再调 SDK；未处理：标记后调 SDK，结果按 ID 缓存
4. 为什么二进制音频流不适合靠内容去重：原始字节流几乎不可能完全相同（重试若重新采样编码，位级内容就变了），内容比对不可靠且成本高，只能靠业务层 ID

- 典型触发场景：HTTP 请求超时后客户端重试，服务端其实已收到第一条，会拿到两条一样的消息——这就是「接口幂等性」要解决的问题

### 16. WebSocket 心跳机制和重连策略

**回答**：

- **为什么需要**：TCP 假死（连接实际断了但没收到 RST/FIN，如弱网、NAT 超时）时两端都感知不到，需要应用层心跳探活
- **心跳**：客户端每 15~30s 发一个小 ping 包，服务端回 pong；收到任何业务消息都重置计时器（有流量说明连接活着，不必额外发心跳）
- **判死**：发出 ping 后超过阈值（如 10s）没收到任何响应，判定连接死亡，主动 `close` 并进入重连
- **重连：指数退避**——第 1 次等 200ms，第 2 次 400ms，第 3 次 800ms……间隔指数级增长，设最大间隔上限和最大重试次数
- **加抖动**：退避时间上叠加随机抖动，防止服务端重启瞬间大量客户端同一时刻重连把服务打垮（惊群）
- 超过最大重试次数后停止重连，提示用户手动刷新

### 17. 为什么不用 WebRTC 做音频传输？它和 WebSocket 底层协议有什么区别

**回答**：

| 维度     | WebSocket                          | WebRTC                          |
| -------- | ---------------------------------- | ------------------------------- |
| 底层协议 | TCP                                | UDP（SRTP）                     |
| 可靠性   | 可靠有序，丢包重传                 | 允许丢包，不保证有序            |
| 延迟     | 丢包时重传导致延迟累积（队头阻塞） | 低延迟，丢了就丢了继续下一帧    |
| 连接模型 | 客户端 ↔ 服务端                    | P2P 为主（STUN/TURN 打洞中转）  |
| 复杂度   | 简单                               | 信令、ICE、编解码协商，复杂得多 |

**当时没用 WebRTC 的原因**：个人项目，求简单够用，且没有浏览器到浏览器的 P2P 需求。

**面试官追问「如果真上线用什么协议」的权衡**：

- 实时语音通话类场景：延迟敏感、丢一两帧可接受 → UDP/WebRTC 更合适
- 但本平台是 **AI 面试场景**：转写文本要交给 AI 做上下文，**一句话丢了 AI 不知道**（人和人说话可以重说，AI 不行），漏字直接影响面试体验 → 准确性优先，TCP/WebSocket 是合理选择
- 技术选型没有绝对答案，讲清楚「业务对丢失和延迟的容忍度」比背协议特性更重要

### 18. axios 封装做了哪些事

**回答**：

1. **基础配置**：`baseURL`、超时时间统一管理
2. **请求拦截器**：统一注入 token 等鉴权头
3. **响应拦截器**：按 HTTP 状态码统一处理——401/403 无权限跳登录页，404 资源不存在，5xx 服务端错误统一提示
4. **文件流特殊处理**：后端文件下载用 blob 返回，文件名放在响应头 `Content-Disposition` 里，需要解析出来拼给下载逻辑；且要**判断响应类型**——成功是 blob 文件流，失败时后端可能返回 HTML 错误页，需要分别处理，否则错误信息会被当文件下载
5. 可扩展方向：重复请求取消（AbortController）、全局 loading 计数、错误码映射

### 19. 大文件下载怎么做？断网后如何续传

**回答**：

- **分片下载**：大文件切成固定大小的片，用 HTTP `Range: bytes=start-end` 请求头逐片请求，服务端返回 `206 Partial Content`
- **断点续传**：每个分片有唯一 ID，下载完成的分片 ID 持久化记录；中断后重新下载时先查记录，已完成的跳过（去重），只从中断的那个分片继续往后请求
- **合并**：全部分片下载完后按顺序拼成完整 Blob，`URL.createObjectURL` + `a[download]` 触发浏览器保存
- 更大文件可考虑流式落盘（`ReadableStream` + File System Access API / StreamSaver.js），避免全部堆在内存

### 20. 如何拦截页面上所有请求？多个包都复写 XHR 会发生什么

**回答**：

**拦截页面所有流量的方式**（安全管控场景）：

1. **Monkey Patch XHR**：保存 `XMLHttpRequest.prototype.open` / `send` 原引用，替换成自己的函数，在自定义逻辑（加安全 header、上报审计、敏感参数检测）执行后再调原函数
2. **Monkey Patch fetch**：同理替换 `window.fetch`
3. axios 的拦截器本质也是这个思路的应用层封装（axios 浏览器端底层基于 XHR）
4. 补充：还有 Service Worker 拦截（作用域内所有请求都过 SW 的 fetch 事件，包括静态资源）、Beacon / WebSocket 需要单独处理

**A、B、C 三个包顺序加载都复写了 XHR，实际请求怎么走**（本场没答好的追问）：

- 会形成**装饰链/洋葱模型**：A 先包住原生 XHR，B 加载后包住「A 包过的 XHR」，C 再包住「B 包过的」
- 请求发出时**依次穿过 C → B → A → 原生 XHR**，响应再沿链返回——即**所有包的拦截逻辑都会执行**，不是只过最后加载的 C
- 前提是每个包都正确保存并调用了上一个引用；如果某个包直接替换而没保存原函数，链就断了，先加载的拦截器全部失效——这也是多个监控/安全 SDK 混用时的经典坑

## 手撕代码

### 1. SSE 流式数据解析

要求：解析 SSE 格式数据流，提取 `data:` 字段内容，处理流式读取中的不完整分片。

```js
// 流式 SSE 解析器：跨 chunk 维护 buffer，保证消息完整
function createSSEParser(onMessage) {
  let buffer = '' // 跨 chunk 的残留数据

  return function feed(chunk) {
    buffer += chunk
    // SSE 事件以 \n\n 为边界
    const events = buffer.split('\n\n')
    // 最后一段没有 \n\n 结尾，说明不完整，留到下次
    buffer = events.pop()

    for (const event of events) {
      const lines = event.split('\n')
      for (const line of lines) {
        if (!line.startsWith('data:')) continue
        const data = line.slice(5).trim()
        if (data === '[DONE]') continue // 结束标记
        try {
          onMessage(JSON.parse(data))
        } catch {
          // 非 JSON 数据（如纯文本心跳），按需处理
        }
      }
    }
  }
}

// 在流读取循环中使用
async function readSSE(response, onMessage) {
  const reader = response.body.getReader()
  const decoder = new TextDecoder('utf-8')
  const feed = createSSEParser(onMessage)

  while (true) {
    const { done, value } = await reader.read()
    if (done) break
    feed(decoder.decode(value, { stream: true }))
  }
}
```

**关键点**：

- **不完整分片处理**：`split('\n\n')` 后 `pop()` 出的最后一段一定是不完整的，留在 `buffer` 里和下个 chunk 拼接后再解析——这是本题的核心考点
- `decoder.decode(value, { stream: true })`：`stream: true` 让 TextDecoder 内部缓存半个 UTF-8 字符（一个汉字 3 字节，可能跨 chunk），防止乱码
- 过滤非 `data:` 开头的行（`event:`、`id:`、`retry:` 字段和注释行）
- `[DONE]` 是模型流式输出的常见结束约定，不应当消息体处理
- 面试时的教训：不要陷进字符串里某个转义引号的细节，先把「按分隔符拆块 → 取 data: 前缀 → 残留缓冲」这个整体框架搭出来

## 反问与面试官建议

**团队业务**：飞书和豆包的账号相关业务。技术栈不强卡前端深度——AI 时代很多跨栈工作都能借助 AI 完成，更看重思维能力和解决问题的能力。

**面试官的两点建议**（值得记下来）：

1. **技术知识要结合实际业务场景**：背面试题时把知识点和自己的业务场景绑定（比如「强缓存用在哪」要能答出 hash 静态资源这个具体场景），既更有说服力，也更容易理解背后的含义
2. **AI 时代代码能力不能丢**：AI 写代码快，但架构和思路容易往上堆叠。如果完全看不懂 AI 在写什么、没有架构梳理能力，项目迟早维护不动；真出紧急问题时只有 AI 能改、改得对不对还没人看得出来——等于把项目撒手托管给 AI，而自己的能力已经不在了
