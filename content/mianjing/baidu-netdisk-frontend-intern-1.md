## 面试问题

### 1. 详细讲讲语音转写的实现

**回答**：整条链路是「浏览器采集 → 格式转换 → 分帧 → WebSocket 传输 → 后端调讯飞 SDK → 结果回推」。

1. **为什么用讯飞**：浏览器Web Speech API 识别准确率不高，后端直接对接讯飞的语音转写服务
2. **建连**：前端先和后端建立 WebSocket 长连接
3. **采集**：用 Web Audio API（`AudioContext` / `getUserMedia`）拿到麦克风的音频流
4. **格式转换**：浏览器采出来的是 **Float32**，讯飞要求 **PCM16**，需要实时转换

```js
// Float32 → PCM16 的转换公式
function floatTo16BitPCM(input) {
  const output = new Int16Array(input.length)
  for (let i = 0; i < input.length; i++) {
    // 先做幅值裁剪，避免溢出失真
    const s = Math.max(-1, Math.min(1, input[i]))
    output[i] = s < 0 ? s * 0x8000 : s * 0x7fff
  }
  return output
}
```

5. **分帧（chunk）**：流式数据不能攒着一次性发，按 **1280 字节一个包**切片，攒够就发，后端逐包调用讯飞 SDK 做流式识别
6. **结果回推**：转写文本再通过同一条 WebSocket 推给前端，页面做打字机式的同步显示

**面试官追问：分 chunk 这一步是你自己做的吗？**

是。音频是字节数组，用一个缓冲区累加，长度达到 1280 字节就截断发送，剩下的留到下一轮，避免出现半包/粘包导致的识别错字。

### 2. 平时使用哪些 AI 编程工具

**回答**：Claude、Cursor、Trae 都在用，其中 **Claude 用得最多**（长任务规划、复杂重构、读大段代码）。

### 3. 用 AI 做过 Code Review 吗？效果怎么样

**回答**：AI 生成代码量大时人工根本看不过来，所以 review 分两层：

- **AI 先做初筛**：让 AI 先过一遍代码，做初步 review
- **自己写测试用例验证**：用生成测试用例的 Skill 产出用例，但**用例本身也要人工扫一遍**
- 重点排查 AI 的「作弊」行为：**有些用例是照着「不管怎么实现都能过」来写的**（断言写太松、mock 掉了被测逻辑），这种用例等于没测
- 用例都真实通过后，基本可以认为这段代码没问题

**一句话**：AI review 只能当「过滤器」，最终的正确性判断必须由人 + 测试用例兜底。

### 4. 你怎么理解 AI？前端工程师应该做哪些准备应对 AI 变局

**回答**：三个层面：

1. **基础不能丢**：手写代码能力、读代码能力是前提。AI 写出来的代码看不懂，那就谈不上用 AI 提效，也谈不上 review
2. **主动理解 AI 的运行机制**：MCP 协议、RAG、大语言模型怎么把指令变成执行——理解原理才知道能力边界在哪
3. **用 AI 提效**：沉淀自己的 Skill / 工具链，探索让多个 Agent **并行工作**的可能性

### 5. 大模型幻觉怎么解决

**回答**：

- **控制上下文**：上下文太长或话题跳跃时容易产生幻觉，多轮对话该新开窗口就新开，不要一条对话里一路缝下去
- **外挂项目规范**：用 `CLAUDE.md` 这类文档约束项目规范，每次开发前先让 AI 加载，让它按规范写而不是自由发挥（相当于外挂了一份 RAG）
- **Prompt 要精准**：输入越精确，产出越可控
- **先规划再执行**：复杂任务走 Plan 模式，先看它规划的方案，合理才让它执行，不合理就让它对着 plan 改

### 6. 为什么上下文越多，模型反而越容易产生幻觉

**回答**：和**注意力机制**有关。上下文越长，注意力被分散的地方越多，模型容易「把指令记混」——**首尾的信息记得比较准，中间部分会变得模糊**（lost in the middle），于是开始编。

不过这个结论有前提：

- 如果始终围绕**同一个问题 A** 继续追问（A、A+、A++），上下文越多，回答其实会**越来越全面精准**
- 但如果一条对话里一会儿问 A、一会儿问 B、一会儿问 C，模型就不清楚当前该聚焦哪个上下文，幻觉概率大幅上升

**所以真正的解法不是「删上下文」，而是「保持话题聚焦」。**

### 7. AI Coding 时不同模型的选取策略

**回答**：按「任务价值 × 成本」分层：

| 环节                | 选型                    | 原因                             |
| ------------------- | ----------------------- | -------------------------------- |
| 技术方案规划 / 架构 | 强模型（Opus 4.8 等）   | 决策错了后面全白干，值得花 token |
| 代码执行 / 编码     | 便宜模型（DeepSeek 等） | 机械劳动，性价比优先             |
| Code Review         | 强模型                  | 审查需要更强的判断力             |

面试官总结我的思路：**从成本开销角度出发，规划环节和审查环节用强模型，执行环节可以用稍弱的模型**。我补充：能用强模型当然全都用强模型最好，分层只是成本约束下的取舍。

### 8. 单 Agent 与多 Agent，了解哪些多 Agent 编排模式

**回答**：使用层面，Claude 遇到复杂任务自己就会开多个 Agent 并行执行；编排层面我知道 LangChain / LangGraph 的几种经典模式：

- **ReAct 模式**：边思考边执行。靠 tool calling 的返回判断任务有没有做完——还需要调工具就继续「思考 → 执行」循环
- **Plan-and-Execute 模式**：先生成完整计划，再一次性执行，后面还可以接一个反思（Reflection）阶段回头检查

**诚实补充**：具体的多 Agent 编排我没有自己设计过，目前属于了解层面。

### 9. MCP、Skills、Rules、RAG 的理解和区别，什么时候用哪个

**回答**：

| 概念      | 解决什么问题                 | 本质                                        | 什么时候用                                       |
| --------- | ---------------------------- | ------------------------------------------- | ------------------------------------------------ |
| **MCP**   | 让模型能**调用外部工具**     | 开放协议，统一模型与外部系统/数据的连接     | 需要操作外部应用、搜索、读数据库等               |
| **RAG**   | 让模型**知道它没学过的知识** | 文档切片 → 向量化入库 → 检索增强生成        | 私有知识库、内部文档问答                         |
| **Rules** | 约束模型**按什么规范做事**   | 项目级规则文件，每次对话自动注入            | 团队编码规范、技术栈约束                         |
| **Skill** | 教会模型**某类任务怎么做**   | 把最佳实践打包成可复用的指令包（提示+脚本） | 组件库使用规范、测试用例生成、前端设计等固定流程 |

**一句话区分**：MCP 给模型**接上手**（能操作外部世界），RAG 给模型**补上知识**，Rules 给模型**划定边界**，Skill 给模型**注入经验**。

### 10. 你自己写过哪些 MCP 或 Skill

**回答**：MCP 没写过，Skill 写过——在实习项目里团队用的是封装好的组件库，必须按照组件库既定的规则使用，否则 AI 会自己乱造组件。

所以我写了一个 Skill，**把「哪个页面该用哪些组件」的映射关系写进去**，AI 在开发时就会按指定组件来写，而不是自由发挥。

- To C：个人 AI 面试平台（响应式，适配了移动端），**但没上线**——调 AI 会产生真实费用，暂时搁置
- H5 / 移动端原生：没有实际项目经验（坦白）
- 小程序：接触过一点，用 **UniApp** 做过（一套代码多端编译）

**追问：小程序包体积有过了解吗？**

当时没答上来，事后补课：

- **单个分包 / 主包 2MB、所有分包总计 30MB** 是硬限制（服务商代开发的小程序总计 20MB），分包（`subPackages`）是核心手段：把非首屏页面拆到分包，主包只留启动必需资源
- **分包预下载**（`preloadRule`）：进入某页面时提前下载后续可能用到的分包，兼顾体积和体验
- **独立分包**：不依赖主包的独立子包，可脱离主包单独运行，进一步降低主包压力
- **资源外移**：图片、字体放 CDN 而不是打包进代码；大图用 WebP、做尺寸裁剪
- **代码层面**：只引入用到的组件库模块（按需引入）、开启 tree-shaking、JS 压缩混淆、去掉 sourcemap
- **分析工具**：微信开发者工具的「代码依赖分析」可以直观看到每个包谁占了大头

### 13. 前端性能优化有哪些方案

**回答**：

- **图片**：懒加载 + 现代格式（WebP / AVIF），按需裁剪尺寸
- **打包分包**：依赖（vendor）和业务代码分包，发版时只更新业务代码包，依赖包 hash 不变、缓存继续命中
- **长列表**：分页；分页不满足业务场景时用**虚拟滚动**，只渲染可视区域，大幅削减 DOM 数量
- **路由懒加载**：一个路由一个 chunk，按需加载，首屏只下载当前页面代码，首屏打开速度明显提升
- **缓存策略**：带 hash 的静态资源设长强缓存，`index.html` 用 `no-cache` 保证入口即时更新

面试官在性能优化这里没有深挖，问完就转到了 SSE / WebSocket。

### 14. SSE 和 WebSocket 怎么保证保活和重连

**回答**：

**SSE（AI 对话场景）**：

- 场景痛点是「AI 生成到一半断了」。我的方案是**不追求自动续传，而是给用户一个明确的重试入口**——提示用户这一轮对话没有完成，用户可以点重试，把之前的对话重新发一次、重新生成
- 这样做的原因是：模型生成是**无状态**的，从头续传需要服务端缓存已生成内容并支持断点，成本高；而对用户来说「重试」是符合直觉的交互

**WebSocket（语音转写场景）**：

- **心跳保活**：客户端每隔 **15 秒**发一个 `ping` 小包，服务端回一个 `pong`，**双向检测**连接是否还活着（防止 TCP 假死——连接断了但没发 RST，两端都感知不到）
- **重连**：检测到断连就发起自动重连，能连上就恢复

面试官总结：**就是互相的保活机制**。

## 手撕代码

题目是一道数组题（语音稿转写有些含糊，题意复原为）：

> 给定一个整数数组，把所有**偶数移到数组末尾**，**奇数移到前面**，且保持各自**原有的相对顺序**不变。
>
> 示例：`[1, 2, 3, 4, 5, 6]` → `[1, 3, 5, 2, 4, 6]`

### 解法：双数组

```js
function moveEvens(arr) {
  const odd = []
  const even = []
  for (const num of arr) {
    // 奇偶分流，各自保持原顺序
    if (num % 2 === 0) {
      even.push(num)
    } else {
      odd.push(num)
    }
  }
  return [...odd, ...even]
}
```

- 时间 O(n)，空间 O(n)
- 天然**稳定**：偶数之间、奇数之间的相对顺序都不变

## 复盘总结

1. **AI 能力已经成为前端面试的独立考点**，而且分量不轻。这场面试里近一半时间在聊 MCP / Skill / RAG / 多 Agent / 幻觉，八股和项目只占了一小部分。**光会用工具不够，要能讲清「什么时候用哪个、为什么」**。
2. **项目里的每个技术决策都要能扛住追问**。语音转写从「为什么用讯飞」一路被问到「分 chunk 这一步是你自己做的吗」，一旦哪一环是别人做的或者抄的，很容易露馅。
3. **没做过的东西直接承认，但要有补课**。H5、移动端、小程序包体积这几个我确实没有实战经验，坦白后把补课内容说清楚，比硬编要好。
4. **反问环节值得认真准备**，这是了解团队真实情况（业务、技术栈、氛围、对 AI 的态度）的唯一机会，也直接影响最后的双向选择。
